## 1. Low-and-slow beyond the link window

Scenario E spaces its steps further apart than the 2 h link window, so consecutive alerts never share an edge and the chain arrives as fragments. Measured: detected on **0/10** seeds, with the best single incident holding 0.20 ± 0.00 of the scenario's alerts. Recorded miss reason: *gaps between steps exceed link_window (2h)*.

**Mitigation (not shipped).** A second, longer window restricted to rare entities (high IDF weight), so a specific account seen twice in a day still links while common entities stay on the short window. Widening the global window instead trades this miss for more over-merging (§7). The bench's temporal-dilation curve (§3–6) measures the same limit adversarially.

## 2. Entity switching across stages

Scenario F uses a different account and source IP at each stage, so no entity is shared between stages. Measured: detected on **0/10** seeds; best incident holds 0.25 ± 0.00. Recorded miss reason: *each stage uses a different account and IP*.

**Mitigation (not shipped).** Link on host continuity (the credential used at stage *n* was harvested on the host where stage *n−1* ran) rather than on shared identity. Entity rotation (§3–6) is the same attack with a tunable budget.

- **Temporal dilation** stretches inter-stage gaps until the median gap is 3× the window at β = 1. The laundering pass cannot help (0.00 vs 0.00 at β = 1) because the missing links are temporal, not entity-based. This is the honest limit of a fixed window; the mitigation is the one in §1.
- **Supernode laundering** routes the shared entity between stages through a stop-listed one. The laundering pass recovers 0.00 → 0.35 at β = 1. It does not recover everything: it only links components whose stages progress forward and share a consistent actor.
- **Entity rotation** gives each stage after the first a fresh account and IP with probability β. At β = 1 recall is 0.50.
- **Noise flood** attacks the scorer, not the correlator: 400 decoy alerts on a criticality-9 asset at β = 1. Recall measures grouping, so the ranking effect is in scenario A's rank per seed: [1,2,2,1,1] at β = 0 and [1,4,2,1,1] at β = 1 (laundering pass on; `-` = not detected).

## 7. Over-merging

Pairwise precision is 0.37 ± 0.17 (pairwise recall 0.90 ± 0.00): many alert pairs the engine puts in one incident belong to different scenarios or to background noise. The engine does not hide this. Cohesion flags 5.70 ± 2.31 incidents per dataset as fragile, and the flag is right — the two halves of the proposed split really belong to different truth groups — **0.67 ± 0.16** of the time. Mean purity of incidents containing scenario alerts is 0.89 ± 0.06.

**Mitigation.** The fragile badge and split preview put the decision in front of the analyst; `POST /incidents/{id}/split` records it in a new run. Not shipped: tightening the stop-list ratio, which trades over-merging for the laundering exposure measured by supernode laundering (§3–6).

## 8. Noise near the top of the queue

On average 0.64 ± 0.05 of the top 10 incidents are dominated by background alerts rather than a planted scenario, and precision@5 is 0.54 ± 0.13. Context, not excuse: each dataset plants only 6 scenarios, so even an engine that returned each as exactly one incident would score at least 0.4 here. Anything above that bound is background incidents outranking planted ones.

Compared with the stated baseline (an analyst reading alerts in timestamp order at 30 s each against incidents in rank order at 180 s each), time to the first real attack still falls by 0.88 ± 0.01.

**Mitigation (partial).** Capacity-calibrated bands keep P1 to what one shift can work, and feedback lowers the precision of noisy rules for the next run. Neither is measured here: every run in this file starts from the default rule statistics.
